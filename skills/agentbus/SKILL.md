# agentbus

Ты постановщик и ревьюер. Исполнитель — OpenCode на хосте — делает работу в
отдельном git-worktree и возвращает отчёт с патчем. Сети у тебя нет: обмен идёт
через каталог, который Cage уже отдал в VM.

## Инструменты

- Клиент: `/home/ruslan/personal/agentbus/bin/cb` (python3, ставить нечего).
- Каталог обмена: `/home/ruslan/personal/.agentbus/cage-claude`, `cb` находит его сам.
  Переменные окружения не нужны — `AGENTBUS_SELF` тоже, отправителя подставляет мост.
- Проверка: `cb env` — покажет пути и число непрочитанных.

## Поставить задачу

```bash
CB=/home/ruslan/personal/agentbus/bin/cb

$CB send --to local-opencode \
  --repo /home/ruslan/personal/real-inflation \
  --meta '{"acceptance":["make check зелёный","тесты на новый случай"],"scope_files":["src/"],"checks":true}' \
  --body "Реализуй T3 по docs/specs/T3.md. Только файлы из спеки."
```

Что важно в постановке:

- `--repo` — абсолютный путь. Исполнитель пускает только `/home/ruslan/personal`
  и `/home/ruslan/gg`, остальное отвергнет.
- `--meta.acceptance` — критерии приёмки списком. Без них исполнитель додумает
  критерии сам, и ты получишь правдоподобный отчёт не о том.
- `--meta.scope_files` — где работать, чтобы он не расползся по репозиторию.
- `--meta.checks: true` — запустить `make check` в worktree. Дорого: поднимает
  Docker. Включай, когда проверка действительно нужна.
- `--base` — от какой ветки/коммита. По умолчанию текущая ветка репозитория.
- `--thread <id>` — продолжить существующий тред вместо нового.
- `--kind task` (по умолчанию), `question` для вопросов без изменений в коде.

Команда печатает `queued_file`; id сообщения узнаешь из `cb inbox`.
Мост забирает файл за пару секунд.

## Забрать результат

```bash
$CB inbox                      # что пришло: id, тип, отправитель, первая строка
$CB show <id> --text           # отчёт и diff_stat
$CB show <id> | jq .meta       # branch, files_changed, checks, usage
$CB patch <id>                 # сам дифф
cat /home/ruslan/personal/.agentbus/cage-claude/inbox/<id>/run.log    # сырой лог
```

Исполнитель работает в ветке `agentbus/<thread_id>`. Он не пушит и не мержит —
это твоё дело и дело человека.

## Ревью и вердикт

- Смотри `patch` и `files_changed`, а не только текст отчёта: отчёт может быть
  бодрее реальности.
- Нашёл проблемы — вердикт. Правка уйдёт в тот же worktree и ту же сессию
  OpenCode, контекст не потеряется:

```bash
$CB reply <id_результата> --kind verdict \
  --body "Не хватает теста на пустой вход. И убери отладочный print в api.py:112."
```

- Вопрос без правок: `$CB reply <id> --kind question --body "..."`.
- Принял: `$CB read <id>` — закрывает сообщение в очереди. Делай это всегда,
  иначе оно висит в `inbox`.

## Когда что-то не так

- `failed` — `cb show <id>` покажет `meta.state_note`: обычно репозиторий вне
  allowlist или в файле постановки не было нужного поля.
- Задача убита по таймауту (40 минут) — отчёт придёт с `timeout: true`, лог в
  `run.log`. Дроби задачу мельче.
- Ответа нет дольше пяти минут на мелкой задаче — скажи человеку: возможно,
  лежит воркер или сервис.
- Патч больше 256 КиБ обрезан: в `meta.patch_bytes` реальный размер,
  `diff_stat` и `files_changed` полные.

## Чего не делать

- Не проси пушить, мержить в `main` или деплоить — этого не будет.
- Не передавай секреты и токены: исполнителю они не нужны.
- Не отправляй задачу без критерия приёмки и без указания файлов.
- Не отправляй одну и ту же задачу дважды — это дубль. Уточняй вердиктом.
- Не считай задачу сделанной, не увидев патч.

## Ограничения

Один исполнитель, задачи идут последовательно: вторая ждёт, пока закончится
первая. Параллельно ставить бессмысленно.
